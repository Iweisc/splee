# Splee spec

Splee is a functional clone of explee.com: an AI outbound agent. You paste your website, a Claude agent researches your company, competitors and buyer segments, finds companies and decision makers on the web, writes personal cold emails, sends them from your own mailboxes within a daily email limit, reads replies over IMAP, classifies them, and auto-replies with your booking link.

- Backend: Rust, Axum 0.8, sqlx + Postgres, `claude-agent-sdk-rs` (drives the local `claude` CLI). `backend/`
- Frontend: Next.js 16 App Router, React 19, Tailwind 4. `frontend/`
- Next rewrites `/api/*` to the backend (`http://127.0.0.1:8787/api/*`), so cookies are same-origin.
- Postgres: `docker compose up -d` (port 55432). Backend: `cd backend && cargo run`. Frontend: `cd frontend && pnpm dev` (port 3333).

Schema: `backend/migrations/`. Rust rows: `backend/src/models.rs`. TS types: `frontend/src/lib/types.ts`. Those three are the contract. Change all three together.

## Conventions

- JSON in and out. Errors are `{ "error": "message" }` with a meaningful status (see `backend/src/error.rs`).
- Money is micro-dollars (`*_micros`, 1 USD = 1_000_000).
- Timestamps are RFC 3339 strings. IDs are UUIDs.
- Lists return `{ "items": [...], "total": n }` when paginated (`?page=1&per_page=50`, page is 1-based). Small fixed lists return a bare array.
- Auth: cookie `splee_session` (extractor `Auth` in `backend/src/auth.rs`). `Auth::project(db, id)` checks org ownership. Admin-only routes call `auth.require_admin()`.
- Public API v1 uses `Authorization: Bearer splee_...` (extractor `ApiKeyAuth`).
- Agent work is always `agent::enqueue(db, kind, project_id, org_id, input)` from routes. Never call Claude inside a request handler, except support chat.
- Splee is free. Sending stops for the day once the project has sent `daily_email_limit` emails or a mailbox reaches its `daily_limit`. Spend in stats is real cost, not credits: `agent_runs.cost_usd` (what Claude Code reports) plus `email_messages.cost_micros`, which is the sending mailbox's `cost_per_email_micros`.

## Agent pipeline (explore run)

One `explore` run executes 6 steps in order and emits `agent_events` as it goes. `agent_runs.step` is the current step (1-6). Each step writes its results to the normal tables as soon as it finishes, so the UI can render partial results.

| step | title (UI) | writes |
|------|-----------|--------|
| 1 | Research your company | `projects.company`, `projects.name` |
| 2 | Explore competitors | `competitors` (up to 12) |
| 3 | Define campaigns | `segments` (4-6, with icon, est_size, fit_score, targeting) |
| 4 | Find potential customers | `companies` for the top segment (demo: 10, app: 25) |
| 5 | Find decision makers | `leads` for the best companies (demo: 6, app: 20) |
| 6 | Write personal emails | `email_messages` drafts, kind `initial`, status `draft` (demo: 3, app: all leads) |

Event kinds: `phase` (data `{step, title, status: "started"|"finished"}`), `log` (short line like `searching "alternatives to larksilk"…`), `tool` (data `{name, input}`), `done`, `error`.

`segments.icon` is one of: `building, store, hotel, heart, palette, home, scissors, briefcase, graduation-cap, stethoscope, factory, truck, utensils, code, shopping-cart, users, landmark, plane, dumbbell, camera`.

`companies.employees` is a display string like `11-50`.

Step 4 and `find_companies` runs also get `mcp__directory__search` when `directory_companies` has rows: an in-process MCP server named `directory` that runs the Companies page's search (`q`, `country`, `city`, `category`, `has_email`, `has_phone`, `limit` up to 50, default 25), leaving out companies the project already has, and returns one line per company with its domain, name, category, place and whether it lists an email or phone. The prompt tells Claude to use it first for local and small businesses and search the web for what it lacks. Its answers go through the same filters and dedupe as web results.

Step 5 and `find_people` runs of a project with Unipile connected also get `mcp__linkedin__people` and `mcp__linkedin__profile`, an in-process MCP server named `linkedin` that replaces the X tools in those calls. `people` takes `company`, `titles` (joined with OR), `location`, `keywords`, `count` (1 to 30, default 10, read in whole pages of 10, at most 3 pages a call) and a `cursor` from its last result, and runs Unipile's classic LinkedIn people search (`POST /linkedin/search` with `api: classic, category: people`): the company and place are first matched to LinkedIn's ids through `GET /linkedin/search/parameters` (`type=COMPANY` or `LOCATION`), and a company only matches a page with the same name, or one that starts with the other, so it never searches another company's people. Titles go in `advanced_keywords.title`. It returns one line per person with their name, headline, current company, location, LinkedIn URL and provider id, leaving out people LinkedIn hides as "LinkedIn Member". `profile` reads `GET /users/{id}?linkedin_sections=experience_preview` by profile link or provider id and shows the headline, location, current positions and websites. The prompt tells Claude to search LinkedIn first for people and copy `linkedin_url` and `linkedin_provider_id` from it, and to check the company's pages when LinkedIn finds nobody. Emails are still found or guessed as before. Each people search page counts in `linkedin_searches` (per Unipile account and UTC day), and an account stops at 100 pages a day with a message saying so.

Step 4, `find_companies` and `find_people` calls also get `mcp__hiring__job_openings`: an in-process MCP server named `hiring` that takes a `domain` and lists the company's open roles from its public job board (title, department, location, date posted, link, newest first, up to 30), or says it has none we can read. It uses the same board detection and cache as the hiring signals worker. The prompt tells Claude a company hiring for a role the offer helps with is a warm prospect and its post a good hook.

The email writer's lead briefs (first emails, follow-ups and LinkedIn sequences) carry `hiring`: up to two open `job_openings` at the lead's company domain, newest first, as `{role, url, excerpt}`. The first-email rules say a matching role usually makes the best first observation, named in plain words, without the link.

### Run inputs (`agent_runs.input`), enqueued by routes, consumed by the agent worker

| kind | input |
|---|---|
| explore | `{mode: "demo"|"app", from_step?: number (default 1), note?: string}` (demo sizes vs app sizes in the table above) |
| find_companies | `{segment_id, count}` |
| find_people | `{segment_id, company_ids?: uuid[], max_per_company?: number (default 2)}` |
| write_emails | `{segment_id?, lead_ids?: uuid[], instructions?: string, follow_up?: bool, rewrite?: bool, drafts?: bool}`. Writes `initial` drafts for leads that have none, approved and queued when the campaign is working or scaling unless `drafts` is set. `follow_up` writes each lead's next follow-up. `rewrite` rewrites each lead's unsent first email or pending follow-up in place, keeping its status. In a campaign with active `segment_variants`, each lead without a variant of its campaign gets one first (`leads.variant_id`, round-robin by count: the active variant with the fewest leads, the first in order on a tie, under a lock on the segment row), and the writer gets one prompt per variant with its instructions last, winning over the default subject, opening and CTA. The email stores `variant_id`. Follow-ups copy the first email's `variant_id` and are told to keep to its angle. |
| classify_reply | `{message_id}` (inbound email_messages row) |
| draft_reply | `{message_id}` |
| linkedin_sequence | `{lead_id}` (connect note + 2 follow-up messages → `linkedin_messages`) |
| explorer | `{query, country?, ip}` → `output.results: ExplorerCompany[]` |
| segment_from_prompt | `{segment_id, prompt}` fills the draft segment's fields |
| social | `{}`. Searches the project's connected X, Reddit, Bluesky, Mastodon and Threads accounts, YouTube videos (`search.list`, `type=video`, published in the last 30 days) as its channel, open questions on the connected Stack Exchange site (`/search/advanced` with `sort=activity`, `fromdate` 30 days back, `accepted=False` and `closed=False`, keeping those with at most 2 answers) as its user, open topics on each joined Discourse forum (`/search.json` with `q` plus `status:open after:{30 days back} order:latest`, read with `/t/{id}.json`) as the forum's user, Lemmy posts and comments (`/api/v3/search` with `type_` `Posts` or `Comments`, `sort=New` and `listing_type=All`, read with `/api/v3/post` and `/api/v3/comment/list`) as its account, and LinkedIn through its Unipile connection, for threads from the last 30 days where its buyers discuss the problem it solves, and drafts up to 10 replies and 2 or 3 original posts into `social_posts` as `draft`. YouTube gets comments on a video or replies to one of its top comments, and Stack Exchange answers to a question, never original posts. DEV gets no tools and no replies, since Forem's API can't write comments, only original articles with a title of at most 128 characters and up to 4 `tags` (lowercase letters and digits). With only DEV connected, the run drafts articles alone. A Discourse forum gets new topics only when a category is picked for it, with `forum` naming it and a title of 15 to 255 characters, and a Lemmy post needs `community` (name@instance, kept in `subreddit`) and a title of at most 200 characters. A Discourse row keeps its forum in `forum_id`. Answers and original posts that mention the company say the writer works on it. A platform that can't sign in is left out, with its error on the integrations page. A reply is kept only when its thread is one the tools showed in the run, isn't locked, archived or closed to replies (a YouTube video with comments off), is at most 30 days old, has no row for the project yet (`in_reply_to` is unique per project) and fits the platform's limit: 280 characters on X, 300 graphemes on Bluesky, the instance's `mastodon_max_chars` on Mastodon, 500 characters on Threads, 10,000 for a YouTube comment, 30 to 30,000 for a Stack Exchange answer, 20 to 32,000 on Discourse, 10,000 on Lemmy, 1250 characters for a LinkedIn comment and 3000 for a LinkedIn post. A Reddit post needs a valid subreddit and a title. `output: {replies, posts}` |

Runs autopilot starts carry `autopilot: true` in their input as well. `research_company` is reserved and unused.

### MCP server (`POST /api/mcp`)

A remote MCP server for ChatGPT, Claude.ai, Claude Code, Cursor and other MCP clients, in `routes/mcp.rs`, over Streamable HTTP without SSE or sessions: every POST carries one JSON-RPC message and gets one `application/json` answer, and GET and DELETE get 405. An `Origin` other than PUBLIC_URL's gets 403. It serves two eras of the spec on the same URL:

- Stateless `2026-07-28`: a request whose `params._meta["io.modelcontextprotocol/protocolVersion"]` (or, without one, `MCP-Protocol-Version` header) names anything but the legacy versions. It needs `_meta` `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` (else 400, -32602) and the headers `MCP-Protocol-Version`, `Mcp-Method` and, for `tools/call`, `Mcp-Name` (`=?base64?…?=` decoded), each equal to the body (else 400, -32020 HeaderMismatch). Another version gets 400, -32022 with `data: {supported: ["2026-07-28", "2025-11-25", "2025-06-18"], requested}`. It answers `server/discover` (`supportedVersions`, `capabilities: {tools: {}}`, `instructions`), `tools/list` and `tools/call`, each result with `resultType: "complete"` and `_meta["io.modelcontextprotocol/serverInfo"]`, discover and tools/list with `ttlMs` (an hour) and `cacheScope: "private"`. Other methods, `ping` included, get 404 with -32601. Notifications get 202.
- Initialize-based `2025-11-25` and `2025-06-18`: `initialize` (whatever headers come with it) answers with the client's `protocolVersion` when it's one of those, else `2025-11-25`, with `capabilities: {tools: {}}` and `instructions` describing the loop. Then `ping`, `tools/list` and `tools/call` with an `MCP-Protocol-Version` of one of those or none, -32601 to anything else, and 202 for notifications and client responses.

Auth is `Authorization: Bearer …` with an API key (`splee_…`, checked like `ApiKeyAuth`) or an OAuth access token issued for `PUBLIC_URL/api/mcp` (below). Without one it's 401 with `WWW-Authenticate: Bearer resource_metadata="PUBLIC_URL/.well-known/oauth-protected-resource/api/mcp"` and a JSON-RPC error, and with a wrong, expired or revoked one also `error="invalid_token"`. Each tool calls the v1 handler for the key's or token's organization, so it has the same org scoping and rules, and returns compact JSON as one text item. A failed call (bad id, an id of another org, a 409) is a result with `isError: true` and the API's error message. An unknown tool is JSON-RPC error -32602. Pages default to 20 items.

### OAuth for the MCP server

The frontend rewrites `/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource[/…]` from the public origin to the API's `/api/.well-known/…`, and sends `Content-Security-Policy: frame-ancestors 'none'` on `/oauth/*`. A refresh token lasts 30 days and works once: it rotates, and using a used one revokes the whole grant. 400 `invalid_grant` for a wrong, expired or revoked code or token, a wrong verifier or redirect URI, or a user who left the org, `invalid_target` for another resource, `unsupported_grant_type`. 401 `invalid_client` for an unknown client or a wrong secret. |
| POST | /oauth/revoke | form `token`, client authentication as above | 200 whatever the token. Either token of a grant revokes the grant. |

A grant is one Allow: an app, a user, an org and the resource. An access token works on the MCP server only (not `/v1`), while it's under an hour old, its grant isn't revoked and its user is still in the org, and it sets the grant's `last_used_at`. It can do what a member can, like an API key.
