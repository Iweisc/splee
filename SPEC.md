# Splee spec

Splee is a functional clone of explee.com: an AI outbound agent. You paste your website, a Claude agent researches your company, competitors and buyer segments, finds companies and decision makers on the web, writes personal cold emails, sends them from your own mailboxes within a daily email limit, reads replies over IMAP, classifies them, and auto-replies with your booking link.

- Backend: Rust, Axum 0.8, sqlx + Postgres, `claude-agent-sdk-rs` (drives the local `claude` CLI). `backend/`
- Frontend: Next.js 16 App Router, React 19, Tailwind 4. `frontend/`
- Next rewrites `/api/*` to the backend (`http://127.0.0.1:8787/api/*`), so cookies are same-origin.
- Postgres: `docker compose up -d` (port 55432). Backend: `cd backend && cargo run`. Frontend: `cd frontend && pnpm dev` (port 3333).

Schema: `backend/migrations/`. Rust rows: `backend/src/models.rs`. TS types: `frontend/src/lib/types.ts`. Those three are the contract. Change all three together.

## Conventions

- JSON in and out. Errors are `{ "error": "message" }` with a meaningful status (see `backend/src/error.rs`).
- Money is micro-dollars (`*_micros`, 1 USD = 1_000_000).
- Timestamps are RFC 3339 strings. IDs are UUIDs.
- Lists return `{ "items": [...], "total": n }` when paginated (`?page=1&per_page=50`, page is 1-based). Small fixed lists return a bare array.
- Auth: cookie `splee_session` (extractor `Auth` in `backend/src/auth.rs`). `Auth::project(db, id)` checks org ownership. Admin-only routes call `auth.require_admin()`.
- Public API v1 uses `Authorization: Bearer splee_...` (extractor `ApiKeyAuth`).
- Agent work is always `agent::enqueue(db, kind, project_id, org_id, input)` from routes. Never call Claude inside a request handler, except support chat and the website chat.
- Splee is free. Sending stops for the day once the project has sent `daily_email_limit` emails or a mailbox reaches its `daily_limit`. Spend in stats is real cost, not credits: `agent_runs.cost_usd` (what Claude Code reports) plus `email_messages.cost_micros`, which is the sending mailbox's `cost_per_email_micros`.

## Agent pipeline (explore run)

One `explore` run executes 6 steps in order and emits `agent_events` as it goes. `agent_runs.step` is the current step (1-6). Each step writes its results to the normal tables as soon as it finishes, so the UI can render partial results.

| step | title (UI) | writes |
|------|-----------|--------|
| 1 | Research your company | `projects.company`, `projects.name` |
| 2 | Explore competitors | `competitors` (up to 12) |
| 3 | Define campaigns | `segments` (4-6, with icon, est_size, fit_score, targeting) |
| 4 | Find potential customers | `companies` for the top segment (demo: 10, app: 25) |
| 5 | Find decision makers | `leads` for the best companies (demo: 6, app: 20) |
| 6 | Write personal emails | `email_messages` drafts, kind `initial`, status `draft` (demo: 3, app: all leads) |

Event kinds: `phase` (data `{step, title, status: "started"|"finished"}`), `log` (short line like `searching "alternatives to larksilk"…`), `tool` (data `{name, input}`), `done`, `error`.

`segments.icon` is one of: `building, store, hotel, heart, palette, home, scissors, briefcase, graduation-cap, stethoscope, factory, truck, utensils, code, shopping-cart, users, landmark, plane, dumbbell, camera`.

`companies.employees` is a display string like `11-50`.

Step 4 and `find_companies` runs also get `mcp__directory__search` when `directory_companies` has rows: an in-process MCP server named `directory` that runs the Companies page's search (`q`, `country`, `city`, `category`, `has_email`, `has_phone`, `limit` up to 50, default 25), leaving out companies the project already has, and returns one line per company with its domain, name, category, place and whether it lists an email or phone. The prompt tells Claude to use it first for local and small businesses and search the web for what it lacks. Its answers go through the same filters and dedupe as web results. `find_companies` runs also get `mcp__places__search` (`agent/places.rs`) when the project's organization has a Google Maps key and calls left under its cap this month: it runs the Local businesses search (`what`, `where`, `min_rating`, `min_reviews`, `limit` up to 60, default 25) with websites only, leaves out businesses the project already has, and returns one line per business with its domain, name, category, address, rating with review count and Google Maps link. The prompt tells Claude it spends the team's own calls, so to use it only when the segment's buyers are local businesses with a storefront or service area, and to use the Maps link as `source_url`.

Step 5 and `find_people` runs of a project with Unipile connected also get `mcp__linkedin__people` and `mcp__linkedin__profile`, an in-process MCP server named `linkedin` that replaces the X tools in those calls. `people` takes `company`, `titles` (joined with OR), `location`, `keywords`, `count` (1 to 30, default 10, read in whole pages of 10, at most 3 pages a call) and a `cursor` from its last result, and runs Unipile's classic LinkedIn people search (`POST /linkedin/search` with `api: classic, category: people`): the company and place are first matched to LinkedIn's ids through `GET /linkedin/search/parameters` (`type=COMPANY` or `LOCATION`), and a company only matches a page with the same name, or one that starts with the other, so it never searches another company's people. Titles go in `advanced_keywords.title`. It returns one line per person with their name, headline, current company, location, LinkedIn URL and provider id, leaving out people LinkedIn hides as "LinkedIn Member". `profile` reads `GET /users/{id}?linkedin_sections=experience_preview` by profile link or provider id and shows the headline, location, current positions and websites. The prompt tells Claude to search LinkedIn first for people and copy `linkedin_url` and `linkedin_provider_id` from it, and to check the company's pages when LinkedIn finds nobody. Emails are still found or guessed as before. Each people search page counts in `linkedin_searches` (per Unipile account and UTC day), and an account stops at 100 pages a day with a message saying so.

Step 4, `find_companies` and `find_people` calls also get `mcp__hiring__job_openings`: an in-process MCP server named `hiring` that takes a `domain` and lists the company's open roles from its public job board (title, department, location, date posted, link, newest first, up to 30), or says it has none we can read. It uses the same board detection and cache as the hiring signals worker. The prompt tells Claude a company hiring for a role the offer helps with is a warm prospect and its post a good hook.

The email writer's lead briefs (first emails, follow-ups and LinkedIn sequences) carry `hiring`: up to two open `job_openings` at the lead's company domain, newest first, as `{role, url, excerpt}`. The first-email rules say a matching role usually makes the best first observation, named in plain words, without the link.
They also carry `tech`, a line like "Uses HubSpot and Intercom" naming the project's tech picks (`project_tech_picks`, in their order) that the company domain's `tech_scans` row lists, left out when none match. The first-email rules say it can open the email when no job post fits, with the tool named plainly and never how we know.
And `why_now`, the first two of the lead's `score_reasons` that aren't `against` (see Lead scores), the same text the user sees on the lead, left out when there are none. The rules say the first sentence may build on one about their company, and never mention a site visit, a page they read, their reply or a deal.

### Lead scores

`score.rs` gives each lead a 0-100 `score`: `score_fit` (0-50) plus `score_intent` (0-50), with no Claude call. Fit is the share of the project's set-up fit signals the company meets, times 50: country (10, the company's or else the lead's `country_code` in every non-empty list of the project's `targeting.countries` and the campaign's `countries`, and not in `exclude_countries`), size (10, `employees` in every non-empty size list), industry (15, the name, description, company database category or lead's company name contains one of the campaign's `industries` or `keywords`, or its singular), tool used (10, the domain's finished `tech_scans` row has a `uses` pick), no competitor (10, it has none of the `competitor` picks, scanned domains only) and title (15, the lead's title contains one of the campaign's `roles`, or has the same seniority: owners and the C-suite, VPs, heads and directors, managers and leads). A signal counts only when the project has it set up, and a lead without a campaign gets every campaign's lists. Intent adds points that halve every few days and stop after a window, capped at 50: hiring (20, half-life 10 days, open `job_openings` first posted in the last 30 days), a site visit (10, 3 days, `visitor_hits` in 14 days), a high-intent page (15, 3 days, a hit on one of `visitor_sites.intent_paths`), a reply classified `question` (20, 7 days, 30 days) and an open deal (25, 30 days). `project_settings.score_signals` turns signals off by key (`country`, `size`, `industry`, `tech`, `competitor`, `persona`, `hiring`, `visit`, `intent_page`, `question`, `deal`). `score_reasons` is up to four `{text, kind}`, the most points first, `kind` `fit` or `intent`, plus a last `against` one when the company uses a competitor: "Hiring 2 SDRs", "Read /pricing yesterday" (days by the project's timezone), "Replied with a question today", "Open deal in Proposal", "Uses a competitor: Calendly". A company's score is its best lead's (by `company_id`, or `company_domain` for leads without one), or its own fit and intent, without title, replies or deals, while it has no leads. The agent's company database tool ranks up to four times its `limit` of listings by the same score and shows the best.

A Tumblr reply is a reblog with the reply as its comment, and only goes to a post that `can_reblog`. A Hashnode article with comments turned off counts as closed. Links are kept as `https://njump.me/note1…` for Nostr, `https://www.tumblr.com/{blog}/{id}` for Tumblr, and the article's URL with `?hashnode={id}` for Hashnode, since its articles live on any domain. Answers and original posts that mention the company say the writer works on it. A platform that can't sign in is left out, with its error on the integrations page. A reply is kept only when its thread is one the tools showed in the run, isn't locked, archived or closed to replies (a YouTube video with comments off), is at most 30 days old, has no row for the project yet (`in_reply_to` is unique per project) and fits the platform's limit: 280 characters on X, 300 graphemes on Bluesky, the instance's `mastodon_max_chars` on Mastodon, 500 characters on Threads, 10,000 for a YouTube comment, 30 to 30,000 for a Stack Exchange answer, 20 to 32,000 on Discourse, 10,000 on Lemmy, 5,000 on Nostr, 4,096 on Tumblr, 10,000 for a Hashnode comment, 1250 characters for a LinkedIn comment and 3000 for a LinkedIn post. A Reddit post needs a valid subreddit and a title. Discord and Telegram take part once a channel is picked for the connected bot: `mcp__discord__search` and `mcp__telegram__search` search the messages `social_messages` holds for the picked channels the bot can read (any keyword, `ilike`, newest first), and `mcp__discord__read` and `mcp__telegram__read` show one with up to 8 messages before and after it. A reply needs a picked channel the bot can post in, kept in `channel_id`, and a post needs `channel`, the chat id of one. They're at most 2,000 characters on Discord and 4,096 on Telegram, and links are kept as `https://discord.com/channels/{guild}/{channel}/{message}` and `https://t.me/c/{id}/{message}`, with `?chat={chat_id}` for a basic group, which has no link of its own. Facebook and Instagram take part once a Page or account is picked and `meta_held_until` has passed: `mcp__facebook__comments` reads each picked Page's 10 latest posts with their 25 latest comments (`GET /{page}/posts` with `comments.limit(25){id,message,from,created_time,can_comment,comments{from}}`) and `mcp__instagram__comments` each account's (`GET /{ig}/media` with `comments.limit(25){id,text,username,timestamp,replies{username}}`), with the Page's token, only on the ones whose user may answer comments (`can_read`). A comment says when its author is a lead in the project, by full name on Facebook and, as a maybe, by the handle in the lead's `x_url` on Instagram, and one the Page or account already answered, or that Facebook says can't take comments, is closed. Links are kept as `https://www.facebook.com/{post_id}?comment_id={comment_id}` and `https://www.instagram.com/p/{shortcode}/c/{comment_id}/?account={ig_user_id}`, which say whose token answers it. A post needs `channel`, a picked Page or account whose user may post (`can_send`), and on Instagram `image_url`, an https link to a JPEG, while a Facebook post may have an https `link`. Answers are at most 8,000 characters on Facebook and 2,200 on Instagram, Page posts 63,206 and captions 2,200. Each client's usage and sign-out are saved after the run, see the social poster. Each connected blog that isn't paused and has room under its `weekly_cap` (counting its articles from the last 7 days that aren't skipped or failed) gets no tools and one article a run, on top of the other posts: platform `blog` with `blog` (the blog's id as listed), a title of at most 200 characters, up to 5 `tags`, an `excerpt` cut to 300 characters and a Markdown body, kept in `blog_id` and `excerpt`. `output: {replies, posts}` |

Runs autopilot starts carry `autopilot: true` in their input as well. `research_company` is reserved and unused.

### Deals pipeline

`deals.rs`, `routes/deals.rs`. Each organization has 1 to 10 `deal_stages` in board order, each `open`, `won` or `lost`, with a `probability` (0-100, 100 for won and 0 for lost) that weights open deals in the forecast. The defaults, Interested (10%), Meeting booked (30%), Proposal (50%), Negotiation (70%), Won and Lost, are created the first time the organization needs a pipeline, once (`organizations.pipeline_seeded`). `deal_stages.auto` marks where a hot reply opens a deal (`hot`, Interested) and where a booking moves it (`booked`, Meeting booked), and follows the stage through renames and reorders. A deal belongs to one lead, whose project it keeps, with `value_cents` and `currency` (the organization's `currency`, USD by default, at creation), `close_date`, `owner_id` (a member), `notes` and `lost_reason`. Its `status` copies its stage's kind, and a unique partial index allows one open deal per lead.

Automatic moves never go backwards and never touch a won or lost deal: a reply classified hot opens a deal in the `hot` stage (else the first open stage) for a lead with no deal at all, and a lead moving to `meeting_booked` (a booking tool, the app or `PATCH /v1/leads/:id`) moves its open deal to the `booked` stage when it's in an earlier one, or opens one there when the lead has no deal. Inserts use `on conflict do nothing` on the index, so two events for the same lead open one deal. Manual moves (`POST /deals/:id/move` and v1) go anywhere, lock the deal's row, set `stage_changed_at` on a change, `closed_at` on closing, clear it on reopening (409 when the lead has another open deal), take the final `value` and the `lost_reason`, and clear the reason when the deal leaves a lost stage. Webhook events, on the project's endpoints and subscribed like the lead events: `deal.created`, `deal.stage_changed` (every stage change), `deal.won` and `deal.lost` (on closing), each with the lead payload, `"reply": null` and `deal: {id, stage, previous_stage, status, value, currency, close_date, owner, lost_reason, url}`. Moves made by saving stages send none.

### Ad audiences

`ads/`, `routes/ads.rs`, migration 0130. A project signs in to LinkedIn (the LinkedIn app from `LINKEDIN_ADS_CLIENT_ID`/`LINKEDIN_ADS_CLIENT_SECRET`, scope `r_ads rw_dmp_segments`), Google Ads (the mailbox sign-in's Google app plus `GOOGLE_ADS_DEVELOPER_TOKEN`, scope `https://www.googleapis.com/auth/adwords`, `access_type=offline`, `prompt=consent` and S256 PKCE) or Meta (the Facebook Page sign-in's Meta app, asking only for `ads_management`), each offered only when the server has its app (`available`). The redirect is `PUBLIC_URL/api/ads/oauth/callback` for all three, with an `ads-oauth` state kept in `ad_oauth_states` and used up like the CRM sign-ins'. The code is traded for tokens (Meta's for a long-lived user token through `meta::Graph::exchange_code`, with no refresh token), and the ad accounts are listed: LinkedIn's `GET /rest/adAccounts?q=search` without `CANCELED` or `REMOVED` ones, Google's `customers:listAccessibleCustomers` with each one's name from a `customer` query (at most 20, managers left out), Meta's `/me/adaccounts`. A sign-in with none is refused. `ad_connections` keeps one per project and platform, the tokens encrypted with APP_SECRET, the listed `ad_accounts`, and the picked `ad_account_id`: the one picked before while the sign-in still lists it, else the only one, else none until the user picks.

Access tokens are renewed like the CRM sign-ins': the stored one while it has a minute left, else the refresh token is traded under an advisory lock per connection, and a request the platform turns down (401, Meta's error 190 or 102) is tried once more with a new token. A refresh token turned down (`invalid_grant`), a token turned down after renewing, any token Meta turns down, or a LinkedIn token that ran out with no refresh token sets `needs_reconnect`, clears the access token and saves the error. Nothing is sent to that platform again until the user signs in again, which keeps the account and audiences.

An audience (`ad_audiences`) is a campaign's on one platform, named "Splee: {campaign}", or the project's hot leads' (`kind` `hot`, "Splee: Hot leads"). Turning one on makes it on the platform right away: a DMP segment with `sourcePlatform` `PARTNER_API` and the LinkedIn destination, a CRM-based Customer Match user list of contact info, or a Custom Audience with `customer_file_source` `USER_PROVIDED_ONLY`. A campaign's holds its leads with an address in `contacted`, `replied`, `hot`, `meeting_booked` or `not_interested`, and the hot leads' audience the project's `hot` and `meeting_booked` leads from every campaign. Neither ever holds a lead whose address, its domain or its phone number is on the org's do-not-contact list, and `new`, `queued`, `unsubscribed`, `bounced` and `do_not_contact` leads are never in one. Each lead goes as the SHA-256 hex of its address trimmed and lowercased, plus for Google the SHA-256 of its number in E.164 (`+447700900123`) and for Meta of its digits with the country code (`447700900123`), when it has one in E.164. Plain values never leave Splee. `ad_audience_members` is a ledger of everyone who may be in each audience, by lead (without a foreign key, so a deleted lead can still be removed), with the hashes sent. A row is written as `adding` before the lead is sent and becomes `added` once the platform confirms it. A sync sends only the difference: first the removals (every lead with a row who is no longer wanted, confirmed or not, and the old hashes of one whose address or number changed), then the additions (every wanted lead not confirmed with its current hashes). Both are harmless to repeat, so a lead from an upload that partly failed is still taken out once they opt out. Batches are at most 5,000 for LinkedIn (`POST /rest/dmpSegments/{id}/users` with `X-RestLi-Method: BATCH_CREATE`, `SHA256_EMAIL` ids) and 10,000 for Meta (`POST` or `DELETE /{audience}/users` with a `payload` of schema `["EMAIL", "PHONE"]`, or `["EMAIL"]` for leads without a number). Both answer straight away, so a removed lead's row goes and an added one is confirmed after each batch. Google applies an offline user data job later and turns down a second job on a list while one runs, so a sync sends one job (`addOperations` 10,000 at a time with `enablePartialFailure`, then `run`), of the removals while there are any, else of the additions, and no consent is sent. Its rows keep the job's resource name, as `adding` or `removing`, until a later sync reads the job's status: `SUCCESS` confirms the additions and drops the removed rows, `FAILED` (or a job Google no longer has) leaves them to be sent again and shows the failure on the audience, and while it's `PENDING` or `RUNNING` nothing more is sent. Syncs, picking an ad account, signing in again, turning an audience off and disconnecting take turns per project and platform (a Postgres session advisory lock on a connection outside the pool), so an account change can't be undone by a sync still running with the old account. A sync then reads the size: LinkedIn's `audienceSize` from the LinkedIn destination, the larger of Google's `size_for_display` and `size_for_search`, Meta's `approximate_count_lower_bound`, kept unless the platform gives none. Turning an audience off, disconnecting, or picking another ad account deletes the audiences on the platform where Splee still can; a new account gets them made again, empty, on the next sync. An audience deleted in the platform's own tools (a 404, or Meta's error 100 with subcode 33) is made again and refilled.

A request answered 429, 503, Google's `RESOURCE_EXHAUSTED` or Meta's errors 4, 17, 32, 613 or 80003 is sent again up to 3 times, waiting `Retry-After` or 2, 4… seconds, at most 30. Meta's usage headers over 90% stop the next call. When the platform keeps asking, the sync stops and `held_until` holds the connection for `Retry-After`, or 15 minutes, between a minute and 6 hours. LinkedIn's 429 `SEGMENT_LIMIT_EXCEEDED` is an error instead. `ADS_API_URL` (Config::ads_api_url) points LinkedIn and Google at one fake under `/linkedin` and `/google` for tests and sandboxes, and Meta uses `GRAPH_API_URL`. The API versions are LinkedIn's `202610` and Google's `v26`.

### Google Sheets

`sheets/`, `routes/sheets.rs`, migration 0133. A project signs in to one Google account for Sheets with the mailbox sign-in's Google app, through the same start and callback (`PUBLIC_URL/api/mailboxes/oauth/callback`, a `sheets-oauth` state in `mailbox_oauth_states` with `purpose` `sheets` and the `project_id`), asking only for `https://www.googleapis.com/auth/spreadsheets openid email`, with `access_type=offline`, `prompt=consent` and S256 PKCE and no `include_granted_scopes`, so its tokens stay apart from any mailbox's. Any member of the project may connect it, unlike a mailbox. `sheet_accounts` keeps one per project, its tokens encrypted with APP_SECRET. Access tokens are renewed like the ad platforms': the stored one while it has a minute left, else the refresh token is traded under an advisory lock per project, and a token Sheets turns down with 401 is renewed once. Google turning the refresh token down (`invalid_grant`), or a fresh token being turned down, sets `needs_reconnect` and `error` ("Google signed Splee out of Sheets…"), and nothing calls Google for the project until it signs in again, which clears both. Each sign-in raises `sheet_accounts.version`, and a request only signs out the version whose token it used, so one that started before a reconnect and fails after it leaves the new sign-in alone. The Sheets API's base is `SHEETS_API_URL` (`https://sheets.googleapis.com` unless set, for tests and sandboxes).

A `sheet_connections` row is a tab, addressed by its title, of kind `import` or `export`. An import has a `mapping` (`{field: column header}`, the fields of a file import, `email` required), a campaign, and `keep_importing`. Its first read happens when it's set up, and with `keep_importing` the worker reads it again every 15 minutes (`next_import_at`). Each read takes the whole tab with `values.get` (formatted values, up to 50,000 rows), the first row as the headers. A row's key is `email:{address}` for a valid email, else `row:{sha256 of its trimmed cells}`, and rows whose key is in `sheet_import_rows` are skipped, so only new rows are read, and a row whose email is filled in later counts as new. New rows go through `util_lead_import::insert` with source `import`, so suppressed, duplicate and invalid addresses are skipped as in any import, and each read that found new rows adds an `imports` row named `Google Sheets: {spreadsheet} › {tab}`. Reads of one connection take turns (advisory lock). A mapped header that's gone fails the read with "The tab has no column called…".

An export has `events`, some of `hot_lead`, `meeting_booked` and `deal.won`. `hooks::send_lead_event` keeps a `sheet_export_rows` row for each export of the project that takes the event, unique per connection, lead and event, with its cells as they were then: Date (in the project's time zone), Event (Hot lead, Meeting booked or Deal won), Name, Email, Company, Campaign, Status, Reply (the event's reply, else the lead's latest inbound message, without the quoted thread, at most 2,000 characters) and Link in Splee. The written row ends with Splee ID, `{lead_id}:{event}`, and so does the header. A tab has at most one export (a unique index on project, spreadsheet and tab). Under a `pg_try_advisory_xact_lock` per connection, so two ticks never write the same row, the worker reads the whole tab once, marks each waiting row (up to 1,000) whose Splee ID is in any cell as written without sending it, and writes the rest in one `values.append` with `valueInputOption=RAW`, putting the header first when row 1 is empty. An append isn't sent again in the same tick after a 5xx or a timeout, since Google may have written it, or still be writing it. Each append notes `sent_at` first, outside the transaction, and the rows wait `export::SETTLE_SECS` (10 minutes) before a read settles them, so a write that lands late is still found. A 429 or a refused token clears `sent_at`, since nothing was written. The same read settles rows Google took when Splee then failed to mark them.

Sheets allows about 60 reads and 60 writes a minute per Google account. A request answered 429 or `RESOURCE_EXHAUSTED`, or a read answered 503, is sent again up to 3 times, waiting `Retry-After` or 1, 2 seconds, at most 30. When Google still refuses, `sheet_accounts.held_until` is set for `Retry-After` or 2 minutes, at most an hour, and nothing calls Google for the project until then. Each connection keeps `last_sync_at`, `rows_added` (leads added or rows written) and the last `error`, cleared by the next success.

### Lead owners

`ownership.rs`. A lead has at most one `owner_id`, a member of its organization. Each project's `assign_rule` (in `/projects/:id/settings`, with `assign_members`) is `off` (the default), `round_robin` or `mailbox`. When a lead with no owner replies by email, LinkedIn or text, books a meeting (in the app, through a scheduling tool or the API) or leaves its email in the website chat, `ownership::claim` gives it one: round robin goes to the member after the last one picked, in `assign_members` order, skipping members who are away or left the team, and locks the `project_settings` row so leads arriving together take turns. By mailbox gives it to the owner of the mailbox that last emailed it, while they're on the team. A lead that has an owner is never moved by a rule. A hot reply's email goes to the owner alone, if their notification settings allow it, instead of everyone (`ownership::hot_lead_recipients`), and the Slack hot-reply post says "for @them" when `users.lookupByEmail` finds their email in the workspace, cached in `slack_user_ids` per workspace and person (a miss is retried after a day, a changed email at once).

### Booking pages

`booking/`, `routes/booking_pages.rs`. Each mailbox can have one `booking_pages` row, a page at `/book/{slug}` for a team without Calendly or Cal.com: `name`, `duration_minutes` (15, 30, 45 or 60), `timezone`, `hours` (seven entries, Monday first, null for a day off, else `[start, end]` in minutes after midnight), `buffer_minutes` (0-120, kept clear before and after every busy time), `notice_minutes` (0-20160), `days_ahead` (1-90), `location` (a video link or where to meet) and `calendar_url_enc`, the secret iCal address of the owner's calendar (Google Calendar's "Secret address in iCal format", an Outlook calendar published as ICS, an iCloud public calendar; `webcal://` reads as `https://`), encrypted like mailbox passwords. Slots start every 15 minutes for 15-minute calls and every 30 otherwise, within each day's hours in the page's time zone (a local time the clocks skip is no slot), at least `notice_minutes` from now, free of the page's other calls and the calendar's busy times with the buffer around them.

The calendar is fetched through `hooks::public_client` (each redirect hop checked, 16 MB at most) and cached in memory for 5 minutes, and a failed fetch keeps the last good copy for an hour and saves the reason in `calendar_error`, which the settings page shows. VEVENTs count as busy unless cancelled or `TRANSP:TRANSPARENT`. All-day events block whole days in the page's time zone, TZIDs are read as IANA names (path prefixes like `/mozilla.org/.../` dropped) or Outlook's Windows names, floating times are in the page's zone, and RRULEs expand with the `rrule` crate minus EXDATEs and the occurrences a second VEVENT with the same UID and a RECURRENCE-ID moved or cancelled. Tests and debug builds with `BOOKING_PRIVATE_CALENDARS=true` fetch from private addresses too, which a release build never does.

Booking checks the slot is free, then takes a per-page advisory lock in the insert's transaction and checks for an overlapping call again, and a unique index on `(page_id, starts_at)` for calls not cancelled backs that up. Each `bookings` row keeps the guest's `name`, `email`, `note` and `timezone`, the `sha256` of the token in its links (`PUBLIC_URL/booking/{token}`, `?cancel=1` to open on the cancel step) and a `sequence`. Both sides get an email from the page's mailbox (the guest's in their time zone, the host's in the page's) with the call as a `text/calendar; method=REQUEST` part and an `invite.ics` attachment: UID `{booking id}@splee`, the mailbox as ORGANIZER, the guest as ATTENDEE with RSVP, the location, and the guest's note and the move-or-cancel link in the description. A move updates the times and bumps `sequence`, so calendars move the event, and a cancellation sends `METHOD:CANCEL`. Nothing is sent with SENDING_ENABLED=false. The org's leads with the guest's email, in any project, go through the same code as the booking webhooks (`routes::bookings::mark_booked` and `mark_cancelled`): a booking moves them to `meeting_booked` with `meeting_at`, firing the chat post, webhook, CRM push and deal move, a move retimes them as "Meeting moved", and a cancellation puts them back to `hot` unless their meeting is at another time.

### Company database

`directory_companies` holds one row per company website from [Overture Maps](https://docs.overturemaps.org/guides/places/)' places, loaded by `splee import-companies [COUNTRY…]` or from the Companies page by instance operators, the users whose email is in `OPERATOR_EMAILS`. It's shared by every organization. The importer reads the newest release's GeoParquet files over HTTPS with range requests, skips row groups whose address countries can't match, and keeps open places that have a website. Pages on platforms like Facebook, Instagram or a booking site aren't the business's own domain, so those are skipped. One place per domain is kept, the one Overture is most confident about. Rows of the imported countries that the new release doesn't list are deleted afterwards.

`directory_imports` is the Companies page's queue: `{country, status, groups_done, groups_total, rows_seen, rows_kept, error, requested_by, started_at, heartbeat_at, finished_at}`, status `queued`, `running`, `done` or `failed`. A unique partial index allows one queued or running row per country, and another allows one running row in the whole table. `groups_total` is the row groups that can hold the country across every file, counted before any rows are read. `rows_seen` counts the places in the groups read and `rows_kept` the companies saved from them, which counts a domain again when several places share it, until the import ends and it becomes the country's number of companies.

### Local businesses

`places.rs`, `local_businesses.rs`, `site_contacts.rs`, `routes/local_businesses.rs`, `agent/places.rs`, migration 0132. An organization pastes its own Google Maps Platform key, encrypted in `places_keys` with its `monthly_cap` (2,000 calls by default). Saving checks it with one Text Search asking for `places.id` only, the free Essentials (IDs Only) SKU, which isn't counted, and Google's refusal comes back in plain words (an invalid key, Places API (New) turned off, billing off, a restricted key, rate limited). A search is `POST {PLACES_API_URL}/v1/places:searchText` with `X-Goog-Api-Key`, an `X-Goog-FieldMask` of id, displayName, types, primaryTypeDisplayName, formattedAddress, addressComponents, location, internationalPhoneNumber, websiteUri, rating, userRatingCount, googleMapsUri, businessStatus and nextPageToken, and `{textQuery: "{what} in {where}", pageSize: 20}`, then `pageToken` for up to 3 pages, Google's limit of 60 a query. Permanently closed places are left out. Phone, website, rating and review count make each call the Text Search Enterprise SKU, `places::PRICE_PER_1000_CENTS` ($35.00 per 1,000), which the cost shown multiplies by the calls, rounded up to a cent, without Google's free monthly calls.

`where` is one place or up to 20 split by new lines or semicolons, each searched on its own and listed once, in order, deduplicated by place id. Each call is counted in `places_usage` (org, UTC month) before it goes out, and refused once the month reaches the cap: when nothing was found yet the search is a 429 saying when it resets, else it returns what it has with that `note`. A place whose pages were all read is kept in `places_searches` (org, lowercased `what` and `where` with spaces collapsed, place ids) and its businesses in `places` (org, place id, name, category, types, address, city, region, country code, lat/lng, phone in E.164 when it reads as one, website, its domain without www, rating, review count, Maps URL) for 30 days, so searching it again calls nothing. Older rows are deleted on the organization's next search. The filters (`min_rating`, `min_reviews`, `with_website`) apply to the kept rows, so changing them is free.

Adding businesses (up to 50) skips ones the project has (a company with the domain or place id, or a lead at the domain or with the phone), ones whose domain or phone is suppressed, ones with neither a website nor a phone, and ones not kept in the last 30 days. Each with a website becomes a `people_found` company with its phone, address and `place_id`, fit reason "Picked from Google Maps" and the Maps URL as `source_url`. Every business gets one `google_maps` lead with the company's name, domain, city, country and phone. For a website, `site_contacts.rs` reads `robots.txt` (Splee's own group, else `*`, longest match wins, `*` and `$` understood), then the homepage and up to two pages it links to on the same site whose address or link text says contact, kontakt, impressum, team, staff, about, people or meet, each only when robots.txt allows its path. Pages are read 10 sites at a time, at most 512 KB each with a 5 second timeout and 12 seconds a site, through public addresses only, and a redirect off the site is dropped. Addresses in `mailto:` links and the text (with `&#64;`, `&commat;` and `%40` read as @) count only at the business's own domain. Someone's own address comes first, a whole name like maria.lopez@ before a single one, then shared ones like hello@ or info@, and the business's own name last. Ones like noreply@, privacy@ or jobs@ are never used. The first that isn't suppressed or another lead's and that the project's verifier doesn't call invalid (at most 3 checked) becomes the lead's email, `verified` when the verifier says so, else `found`, with `email_source` `Website` and the person's name when the address spells one. When none will do but an address named someone, the lead gets that name and `email_search` `queued`, so the email finders look for their address. Otherwise it's `not_found` with why. A business without a website is a lead with only its phone, for calls and texts.

### MCP server (`POST /api/mcp`)

A remote MCP server for ChatGPT, Claude.ai, Claude Code, Cursor and other MCP clients, in `routes/mcp.rs`, over Streamable HTTP without SSE or sessions: every POST carries one JSON-RPC message and gets one `application/json` answer, and GET and DELETE get 405. An `Origin` other than PUBLIC_URL's gets 403. It serves two eras of the spec on the same URL:

- Stateless `2026-07-28`: a request whose `params._meta["io.modelcontextprotocol/protocolVersion"]` (or, without one, `MCP-Protocol-Version` header) names anything but the legacy versions. It needs `_meta` `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` (else 400, -32602) and the headers `MCP-Protocol-Version`, `Mcp-Method` and, for `tools/call`, `Mcp-Name` (`=?base64?…?=` decoded), each equal to the body (else 400, -32020 HeaderMismatch). Another version gets 400, -32022 with `data: {supported: ["2026-07-28", "2025-11-25", "2025-06-18"], requested}`. It answers `server/discover` (`supportedVersions`, `capabilities: {tools: {}}`, `instructions`), `tools/list` and `tools/call`, each result with `resultType: "complete"` and `_meta["io.modelcontextprotocol/serverInfo"]`, discover and tools/list with `ttlMs` (an hour) and `cacheScope: "private"`. Other methods, `ping` included, get 404 with -32601. Notifications get 202.
- Initialize-based `2025-11-25` and `2025-06-18`: `initialize` (whatever headers come with it) answers with the client's `protocolVersion` when it's one of those, else `2025-11-25`, with `capabilities: {tools: {}}` and `instructions` describing the loop. Then `ping`, `tools/list` and `tools/call` with an `MCP-Protocol-Version` of one of those or none, -32601 to anything else, and 202 for notifications and client responses.

Auth is `Authorization: Bearer …` with an API key (`splee_…`, checked like `ApiKeyAuth`) or an OAuth access token issued for `PUBLIC_URL/api/mcp` (below). Without one it's 401 with `WWW-Authenticate: Bearer resource_metadata="PUBLIC_URL/.well-known/oauth-protected-resource/api/mcp"` and a JSON-RPC error, and with a wrong, expired or revoked one also `error="invalid_token"`. Each tool calls the v1 handler for the key's or token's organization, so it has the same org scoping and rules, and returns compact JSON as one text item. A failed call (bad id, an id of another org, a 409) is a result with `isError: true` and the API's error message. An unknown tool is JSON-RPC error -32602. Pages default to 20 items.

### OAuth for the MCP server

Splee is the authorization server of its own MCP server, in `routes/oauth.rs`, following the `2026-07-28` authorization spec: OAuth 2.1 authorization code with S256 PKCE only, RFC 9728, RFC 8414, client ID metadata documents and RFC 7591 registration, RFC 8707 resources, RFC 9207 `iss` and RFC 7009 revocation. The frontend rewrites `/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource[/…]` from the public origin to the API's `/api/.well-known/…`, and sends `Content-Security-Policy: frame-ancestors 'none'` on `/oauth/*`. The issuer is `PUBLIC_URL` without its trailing slash.

| method | path | body / query | response |
|---|---|---|---|
| GET | /.well-known/oauth-protected-resource, /.well-known/oauth-protected-resource/api/mcp | | `{resource: PUBLIC_URL/api/mcp, authorization_servers: [issuer], bearer_methods_supported: ["header"], resource_name}` |
| GET | /.well-known/oauth-authorization-server | | `{issuer, authorization_endpoint: PUBLIC_URL/oauth/authorize, token_endpoint, registration_endpoint, revocation_endpoint (PUBLIC_URL/api/oauth/…), response_types_supported: ["code"], grant_types_supported: ["authorization_code", "refresh_token"], code_challenge_methods_supported: ["S256"], token_endpoint_auth_methods_supported and revocation_endpoint_auth_methods_supported: ["none", "client_secret_post", "client_secret_basic"], client_id_metadata_document_supported: true, authorization_response_iss_parameter_supported: true}` |
| POST | /oauth/register | JSON `{redirect_uris, client_name?, token_endpoint_auth_method?, grant_types?, response_types?}` | 201 with the client and a UUID `client_id`, plus `client_secret` (stored hashed, `client_secret_expires_at: 0`) unless the method is `none`. The method defaults to `client_secret_basic` as RFC 7591 says. 400 `invalid_redirect_uri` unless there are 1 to 10, each https, or http on localhost, 127.0.0.1 or [::1], without a fragment or credentials. 400 `invalid_client_metadata` for another method, grant or response type. |
| GET | /oauth/authorize | the authorization request (session) | `{client_name, client_host, redirect_host, local}` for the consent page, or `{redirect}` with an OAuth error for the app. A `client_id` that is an https URL with a path, spelled as parsing spells it, names a metadata document, fetched from a public address (5 s, 64 KB, no redirects) when unknown or read over an hour ago and kept in `oauth_clients`. The document's `client_id` must be its URL and it needs `client_name` and an https or loopback `redirect_uris`, and may not ask for a client secret. Until the app and its redirect URI check out it's 400 with the error shown on the page, never a redirect. `redirect_uri` must equal a registered one, except that a loopback one may name any port (RFC 8252), and may be left out when there's one. Then `response_type=code`, a 43-character `code_challenge` with `code_challenge_method=S256` and a `resource` (optional, compared without case in scheme and host or a trailing slash) of `PUBLIC_URL/api/mcp`, else the redirect carries `unsupported_response_type`, `invalid_request` or `invalid_target`. |
| POST | /oauth/authorize | JSON: the same parameters plus `{allow, org_id?}` (session) | `{redirect}`: with `code` (5 minutes, stored hashed with the user, the org, the redirect URI, the challenge and the resource), or `error=access_denied`. Every redirect carries the app's `state` and `iss`. 403 when the user isn't in `org_id`, which defaults to the session's. |
| POST | /oauth/token | form, with `client_secret_basic`, `client_secret_post` or a public `client_id` | `authorization_code` (`code`, `code_verifier`, optional `redirect_uri` and `resource` that must match the code's) or `refresh_token` → `{access_token: "splee_at_…", token_type: "Bearer", expires_in: 3600, refresh_token: "splee_rt_…"}`, `Cache-Control: no-store`. A code works once for its client, and a second use revokes the grant it made. A refresh token lasts 30 days and works once: it rotates, and using a used one revokes the whole grant. 400 `invalid_grant` for a wrong, expired or revoked code or token, a wrong verifier or redirect URI, or a user who left the org, `invalid_target` for another resource, `unsupported_grant_type`. 401 `invalid_client` for an unknown client or a wrong secret. |
| POST | /oauth/revoke | form `token`, client authentication as above | 200 whatever the token. Either token of a grant revokes the grant. |

A grant is one Allow: an app, a user, an org and the resource. An access token works on the MCP server only (not `/v1`), while it's under an hour old, its grant isn't revoked and its user is still in the org, and it sets the grant's `last_used_at`. It can do what a member can, like an API key.


### Deliverability

| method | path | body | response |
|---|---|---|---|
| GET | /deliverability | | `{checked_at, domains, mailboxes, series, postmaster}`. `domains`: the org's registered sending domains and mailbox domains, each with `verdict` (`good`, `watch` or `at_risk`, the worst of its own `reasons` and its mailboxes'), `reasons`, `listings` (its own and its mailboxes' sending IPs': `{list, label, kind, target, status: clear \| listed \| unknown, detail, delist_url, checked_at}`), `postmaster` (its latest `postmaster_days` row) and `mailboxes` (a count). `mailboxes`: each with `verdict`, `reasons` (its domain's and its own, each `{code, level, text, fix}`), `held`, `last_error`, `week` and `month` `{emailed, bounced, opted_out, replied}` by lead, `ips` and `ip_source` (`received` or `smtp_host`). `series`: all domains together (`domain: ""`) then each domain, 30 UTC days of `{date, bounce_rate, opt_out_rate, spam_rate}`, the first two over the 7 days ending that day, `spam_rate` Gmail's that day (the highest across domains for all). `postmaster`: `{available, connection: {email, domains, error, synced_at, signed_out} \| null}`. |
| POST | /deliverability/check | | The same, after checking the blocklists, syncing Postmaster and judging the mailboxes now. Admins only. |
| POST | /deliverability/postmaster/oauth | | `{url}`, Google's sign-in with scope `postmaster.readonly openid email`, through the mailbox sign-in's Google app, state and callback (`mailbox_oauth_states.purpose = 'postmaster'`). The callback saves `postmaster_connections`, syncs once and redirects to `/app/deliverability?postmaster=connected` or `?postmaster_error=<message>`. Admins only. |
| DELETE | /deliverability/postmaster | | `{ok}`, removing the sign-in and its `postmaster_days`. Admins only. |

Reasons and their lines live in `deliverability/thresholds.rs`. Bounce rate (by lead, over the week once it emailed 20 leads, else the 30 days) above 2% is watch and above 3% at risk. Opt-outs (replies classified `unsubscribe` and unsubscribe clicks by leads the mailbox emailed) above 2% watch, above 5% at risk. Under 1% replied over 30 days, with at least 100 leads, is watch, and so is warmup landing in spam. A listing on Spamhaus DBL, SURBL, URIBL, Spamhaus ZEN or Barracuda is at risk, on SpamCop watch. From a Postmaster day in the last 7: reputation Medium watch, Low or Bad at risk, spam rate above 0.1% watch and above 0.3% at risk, and SPF, DKIM or DMARC under 98% watch. Lists are asked with A queries through the system resolver: `{domain}.dbl.spamhaus.org`, `{domain}.multi.surbl.org`, `{domain}.multi.uribl.com`, and the reversed IPv4 under `zen.spamhaus.org`, `b.barracudacentral.org` and `bl.spamcop.net`. NXDOMAIN is clear. Spamhaus's 127.255.255.x and SURBL's and URIBL's 127.0.0.1 (a refused or public resolver), answers outside 127/8 and failed lookups are `unknown`, never listed. URIBL's grey list isn't a listing.

Each lead records `email_source` (finder or pattern), `phone_source` when a finder filled its phone, `email_search_note`, `email_search_lookups` and `email_search_credits` (only Anymail Finder, LeadMagic and Lusha report them). A lead is searched once unless it's queued again.
- Hiring signals (hourly): for each project with an organization that watches some roles (`project_settings.targeting.hiring_roles`, a list of job titles, defaults to its campaigns' `roles` when unset, and an empty list turns it off), checks its company domains (non-excluded `companies` plus leads' `company_domain`) that weren't checked in the last day, never-checked first then oldest-checked, at most 500 a project in any 24 hours (`hiring_checks`), 4 at a time. A domain's board comes from `job_boards`, found the first time from Greenhouse, Lever, Ashby, Workable or Recruitee links on its homepage, `/careers` and `/jobs`, else by trying the domain's first label (and that without hyphens) as a slug on each, with an 8-second timeout and the user agent `Mozilla/5.0 (compatible; Splee job board check)`. A domain with none is tried again after 14 days, and a board that answers 404 is detected again. Openings whose title contains a watched role as whole words in order (a plural counts) are upserted into `job_openings` by `(project_id, url)` with the first role they match as `role`, moving `last_seen` and clearing `closed_at`. Openings the board no longer lists, or every one when the domain has no board any more, get `closed_at`. A board that can't be read leaves them alone until the next day.
- Tech signals (every 10 minutes): for each project with an organization, oldest first, under a per-project advisory lock (`pg_try_advisory_xact_lock`, so a second backend moves on to another project), takes its company domains (non-excluded `companies` plus leads' `company_domain`) that `tech_scans` has never seen, last took over 30 days ago, or took over a day ago without finishing, never-taken first then oldest, up to what's left of 300 an hour across every project (rows whose `checked_at` is in the last hour, counted and taken under one global advisory lock). Taking a domain sets `checked_at`, so a domain shared by projects or organizations is fetched once. Each scan, 4 at a time, GETs `https://{domain}` and then `https://www.{domain}` when that fails, following up to 4 redirects by hand through `hooks::public_client` so every hop is a public address, with an 8-second timeout, the user agent `Mozilla/5.0 (compatible; Splee tech check)` and the first 2 MB of the body, and looks up the domain's MX and TXT records with the resolver the mailbox DNS check uses. `fingerprints::detect` matches about 160 tools by src and href hosts, the meta generator, response headers, cookie names, HTML markers, MX hosts, SPF includes and domain-verification TXT records, with no Claude call, and the names go in `techs` in catalogue order with `scanned_at`. A homepage that couldn't be read keeps the tools earlier scans found and adds what DNS showed.
- Lead scores (every 60s): for each project with an organization and some leads or companies, under a per-project advisory lock, scores it again when it wasn't scored in the last 10 minutes and either something it reads changed since `project_settings.scored_at` (new leads, companies, attributed `visitor_hits`, `job_openings` first seen or closed, received emails, deals opened, moved or closed, or `score_inputs_at`, which the targeting, tech picks and score signals set) or it wasn't scored in the last hour, so intent fades. Facts come from four set-based queries (companies, leads with their latest question and open deal, and per-domain scans, posts, visits and high-intent hits), the scores are worked out in Rust and written back 5,000 rows a statement through `unnest`, touching only rows whose score changed (`scored_at` is when it last changed). Companies without leads get their own score, then each company with leads gets its best lead's in one update.
- Hot visitors (on each attributed hit): when the project has `intent_paths` and the company read one of them today (UTC, the path itself or one under it), and its project company or one of its leads is in a campaign or it has 3 or more hits today, `visitor_alerts` claims (project, domain, day) and the alert goes to the project's chats (`hooks::post_chat`), linking to `/app/p/:id/companies?tab=visitors`. Once per company per UTC day. The hourly visitor data cleanup deletes `visitor_hits` older than 180 days, `visitor_networks` older than 30 and `visitor_alerts` from before yesterday.
- Optimizer (hourly): per working segment with >= 40 sent emails, sent emails per hot lead < 250 → `scaling`, > 625 → `paused` (once: `auto_paused_at` records it, and a campaign you resume afterwards stays `working`), else `working`. Scaling segments get first pick in the sender. Then A/B auto-pick: per segment with `variant_pick_after` set and no pick yet, once there are two or more active variants, each with at least that many sends (and 30), and the leader beats every other at 95% (as in `GET /segments/:id/variants`), the others get `paused_at` and the segment records `variant_winner_id`, `variant_picked_at` and `variant_pick_note`. Written emails are left alone.

## Browser extension

`extension/` is a Manifest V3 extension for Chrome, Edge and Firefox 128+, plain JavaScript with no build step. Permissions: `activeTab`, `storage` and `scripting`, with the Splee origin asked for as an optional host permission at sign-in (the CORS above covers a refusal). `chrome.storage.local` keeps the Splee origin, the API key and the last project and campaign. Nothing runs on pages until the popup opens: it then injects `selectors.js` and `readers.js` into the active tab and calls `spleeRead(document, location.href)`, which only reads the DOM already loaded. A LinkedIn `/in/:id` page gives `{kind: person, name, title, company, linkedinUrl}` (the top card, then the signed-out title `Name - Company | LinkedIn`, then the headline's "Title at Company"), a `/company/:slug` page `{kind: company, name, domain, size, sourceUrl}` (the About section's Website and Company size, then the top card, unwrapping `linkedin.com/redir/redirect?url=`), any other LinkedIn page nothing, and any other http(s) page `{kind: site, name, domain, emails, sourceUrl}` (name from `og:site_name`, `application-name`, then the title part matching the domain; up to 10 `mailto:` addresses, the site's own first). `selectors.js` holds every LinkedIn selector with fallbacks. The popup checks with `/v1/extension/check` on open and as fields change, then adds a person with `/v1/extension/leads`, a company with a picked address the same way, and one without with `/v1/extension/companies`. A 401 signs it out. `npm test` runs the readers against `extension/test/fixtures` in a vm with linkedom, and `npm run -s package` zips the loaded files into `dist/splee-extension.zip`. The API keys page's Browser extension card has the install steps, the Splee address and a shortcut that opens Create key named "Browser extension".
